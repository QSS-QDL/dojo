## 一、认出它：序列化数据格式指纹表

| 格式 | 十六进制开头 | base64 开头 | 出现位置 |
|---|---|---|---|
| **Java 原生** | `AC ED 00 05` | `rO0AB` | cookie（rememberMe 解密后）、POST body、RMI/JMX/T3 流量、HTTP 头 |
| **.NET BinaryFormatter/ViewState** | `00 01 00 00 00 FF FF FF FF` | `AAEAAAD` / ViewState 常见 `/wEP` | `__VIEWSTATE` 隐藏字段、Cookie |
| **PHP serialize** | 文本 | `Tzo4Oi`（O:8: 的 b64） | cookie、session 文件、数据库字段、`a:2:{` 开头明文 |
| **Python pickle** | `80 04 95`（协议4）/ `80 02` | `gASV` / `cos` | Celery 消息体、session 后端、缓存（Redis 里的 value!） |
| **Ruby Marshal** | `04 08` | `BAh` | cookie（`_session_id`） |
| **Node serialize** | 文本 `{"rce":_$$ND_FUNC$$_function` | — | 老库 node-serialize/funcster |
| **Fastjson 入口** | 文本 JSON 含 `@type` | — | 任何 JSON 接口（03 篇 §五） |
| **XStream** | XML `<xxx>` + 历史 CVE 报错 | — | XML 接口 |
| **Jackson** | JSON + `enableDefaultTyping` 历史配置 | — | JSON 接口（`["类名",{...}]` 多态格式是招牌） |

**判定动作**：抓包看到 base64 → 解码看开头（`echo xxx | base64 -d | xxd | head -2`）→ 对上表 → 进入对应分节。**「这是什么编码」的判定 3 秒完成，是反序列化猎手的第一反射。**

## 二、Java 原生反序列化

### 【判定与证明】（分级红线表——与 02 篇 Redis 同款纪律）

| 级 | 动作 | 做不做 |
|---|---|---|
| 1 | 识别格式（rO0AB） | ✅ 报告素材一 |
| 2 | **URLDNS 链探测**：构造只触发 DNS 解析的无害链（ysoserial URLDNS），指向你的 dnslog → 回连 = 「存在反序列化入口+可触发+出网」三合一 | ✅ **标准最小证明，到此即高危成立** |
| 3 | 依赖清单确认链可用性：从报错/heapdump/.git 找 Commons-Collections/BeanUtils 等版本 → 对照 gadget 适配表 | ✅ 增强报告（「CC 3.2.1 在依赖中，存在成熟利用链」） |
| 4 | 实际利用链（CC/TemplateImpl/JdbcRowSet）执行命令 | ❌ **绝对越线**（=RCE 执行，只属于本地靶场） |
| 5 | 内存马/持久化 | ❌❌ 见 §五 |

### 【入口清单】（哪里会有序列化数据流进来）
```
HTTP: rememberMe(Shiro) · __VIEWSTATE 类自研加密参数 · body 的 Content-Type: application/x-java-serialized-object
协议: RMI(1099) · JMX(7199/9999) · T3/IIOP(WebLogic 7001) · Dubbo(20880) · Redis 里 Java 应用存的 value
文件: 上传的 .ser/会话文件/缓存文件被应用重新加载
```

### 【Shiro / Fastjson / Jackson 专项】见 03 篇 §二/§五——判定探针（deleteMe/DNSLog @type）在那边，本篇不重复。**三者的关系**：Shiro=「加密壳+默认key」问题，Fastjson/Jackson=「JSON 多态类型」问题，原生=「二进制格式」问题——三条河都汇到同一个海：**类型系统被数据操控**。

## 三、.NET ViewState / PHP POP / Python pickle（识别级+证明级）

### .NET ViewState
```
判定: 页面含 __VIEWSTATE 隐藏字段（ASP.NET WebForms 招牌）
解码: base64 → AAEAAAD 开头 = BinaryFormatter 流
攻击前提: machineKey 泄露（web.config 泄露/默认 key/heapdump）→ 可签名恶意 ViewState
证明级: ①解出 ViewState 内容（无需 key，可读=信息泄露证据）②macgenerator 检查是否启用 MAC 校验
        （老配置 EnableViewStateMac=false → 无需 key 直接注入=高危；该开关已被微软强制，存量老系统仍有）
红线: 构造恶意 ViewState 执行命令 = 级4，不做；「MAC 未启用+可解析」已是完整证据
工具: ysoserial.net（本地研究）· viewgen（key 已知时的生成器）
```

### PHP POP 链
```
判定: O:8:"Xxx":1:{...} 或 base64 的 Tzo4Oi（§一 表）
入口: cookie/session/参数里可控的序列化串被 unserialize()
链的本质: __destruct/__wakeup/__toString 魔术方法链，把「属性赋值」传导到「危险调用」（eval/include/system）
证明级: ①识别 unserialize 入口（报错/行为差异）②依赖库有已知链（phpggc 清单比对：
        Laravel/Guzzle/Monolog/ThinkPHP 各有公开链）——「入口+可用链」= 高危证据
红线: 同 Java 级4——链的真实执行不做；phpggc 的 -o 输出到 dnslog 类无害探测可用
审计视角（比打更值钱）: grep unserialize → 追参数来源（02_心智模型/01 反向追踪）→ 看 __wakeup 绕过面
        （CVE-2016-7124 类：序列化串里属性数不符跳过 __wakeup——字符串逃逸的基础，你的 CTF 存量）
```

### Python pickle
```
判定: gASV 开头 base64 / Redis-Celery 组合（任务队列消息=pickle 是常态）
入口: session 后端(pickle serializer) · Celery/Redis 队列 · 上传的模型文件(.pkl 机器学习模型=pickle!)
证明级: 识别入口 + 依赖版本；__reduce__ 机制说明写入报告
红线: pickle 执行=任意代码执行，无任何「半无害」中间态——识别到入口直接报告，不构造 payload
新面: AI 生态的模型文件投毒（.pkl/.pt 加载面）——你的 AI 安全速通（dojo 06/01）会再遇到它
```

## 四、XStream / Jackson / YAML（配置与数据格式面）

| 库 | 判定 | 高危面 | 证明级 |
|---|---|---|---|
| XStream | XML 接口报错含 `com.thoughtworks.xstream` | CVE 清单长（1.4.x 系列反复修，CVE-2021-39144 等） | 版本号判定（报错/依赖）→ 对照 CVE → 报告「版本受影响」，不打链 |
| Jackson | JSON 多态 `["com.xx.Class",{...}]` 格式 | `enableDefaultTyping` 开启时的 JdbcRowSetImpl(JNDI)/TemplatesImpl 链 | 判定多态格式存在 → 报告配置缺陷 |
| SnakeYAML | `.yml` 上传/配置接口 | `!!javax.script.ScriptEngineManager` 类构造器注入 | 识别 YAML 解析入口即报告「存在构造器注入面」 |
| Log4j2/JNDI | （03 篇 §五） | `${jndi:ldap://}` | DNSLog 回连即停 |

**共同模式**：这三家都是「数据格式携带类型信息 → 类型实例化即执行」——**JNDI 是 Java 生态的万能出口**（ldap/rmi/dns），所以 DNSLog 探针在 Java 世界几乎万能。

## 五、内存马：技术、边界、检测（三段分开写）

### 技术概念（理解级，服务判定与报告）
```
本质: 不写文件，向运行中的容器/框架动态注册一个恶意处理组件——
  Filter/Servlet 型（Tomcat/Java 标准组件）· Valve 型（Tomcat 管道）· Listener 型 ·
  Spring Controller/Interceptor 型（注解容器动态注册）· Agent 型（JVM Instrumentation，最深）·
  中间件特有型（WebLogic/Websphere 各自组件）
为什么难检测: 无文件落地，重启即消失（既是它的弱点也是它的隐蔽性）
注入前提: 已有代码执行能力（RCE 后的持久化手段）——所以「内存马」永远出现在「已沦陷」语境
```

### 边界（为什么 SRC 场景绝对不用）
1. **改变运行状态**：向生产 JVM 注入组件=修改系统（红线「不破坏业务」）；
2. **持久化=后门**：无论意图，效果等同留后门（红线「不留后门」，01 篇 §16）；
3. **不可控风险**：注入失败可能崩服务；被第三方检测到你「种马」的记录，性质从测试变攻击；
4. 你的 27 天计划早已写明：内存马只在本地靶场验证技术。**报告需要 RCE 证据时，命令回显/DNSLog/文件读三选一，永远轮不到内存马。**

### 检测视角（防御面——写进报告的加分项，也是你甲方侧能力）
```
思路: 运行时组件枚举与基线比对——
  ① 列出现有 Filter/Servlet/Valve（JMX/agent dump/框架 API），比对部署时清单，多出来的=可疑
  ② 类加载器异常（匿名类/动态定义类，无对应 .class 文件来源）
  ③ 请求处理时间异常（某 Filter 对所有请求生效但无业务意义）
  商用/开源工具生态: ARTHAS(阿里,sc/sm 命令查类来源) · 各类 copagent/内存马查杀工具
报告用法: 「已验证 RCE 能力（DNSLog）。提示：该漏洞可被用于注入内存马实现无文件持久化，
          建议排查 Filter/Servlet 注册表并参考 ARTHAS 类来源审计。」——这段话让你从「报洞的」升级成「懂对抗的」
```

## 【本篇学习建议】

1. **学习路径严格按 J02 走**（原理→链构造→利用），本篇是它的「实战判定与红线」伴侣卷。顺序：vendor/JavaGuide 三篇（反射/序列化/代理）→ J02 → 本篇 §一 指纹表背熟 → vulhub 反序列化系环境全通（**本地随便打，链随便造**——技术在靶场练透，边界在实战守死）。
2. §一 的指纹表值得做成 Anki 卡（8 行，视觉化记忆：base64 开头四字符）——「rO0AB / AAEAAAD / gASV / Tzo4Oi」四个词是你的第一层条件反射。
3. URLDNS 无害链的构造原理搞懂（HashMap+URLStreamHandler 的 hashCode 触发链，不需要任何危险类）——它是「证明级安全」的设计典范，也是你理解 gadget 机制的最佳入门样本。
4. 内存马的检测段（§五.3）建议深学：它让你未来能接「应急响应」类的活（B 路线能力项），且完全在防御侧，零合规风险。
