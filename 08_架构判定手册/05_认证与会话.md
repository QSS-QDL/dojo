# 05 · 认证与会话全谱：判定 · 测试 · 绕过 · 学习

> 覆盖：Cookie/Session · JWT · OAuth2/OIDC · SSO/CAS/SAML · 密码策略与找回流程 · 多因素（MFA）。
> **这是你智库最薄（认证/JWT 仅 75 篇）、SRC 出单最多（边界⑦⑧）的一册**，也是「不需要任何 payload 就能出高危」的一册。

## 一、总判定：先给目标的认证体系画像（5 个只读请求内完成）

```
① 凭证存哪：Set-Cookie（HttpOnly?）/ localStorage（JS 可读）/ URL 里（灾难）
② 会话标识长什么样：随机串（服务端 session）/ JWT（自包含）/ 加密串（Shiro rememberMe 类）/ 可预测（自增、时间戳）
③ 状态在服务端还是客户端：改 cookie 值后行为变化 = 服务端查表；解出结构自明 = 客户端信任
④ 谁在鉴权：网关（统一 302→/login）/ 框架 filter / 应用代码 / 前端路由（最危险）
⑤ 有没有第二通道：APP/小程序/API 直连（常绕过 Web 侧加固）
```

**画像结论直接决定测试路径**：客户端信任 → 打签名/加密（§三 JWT）；服务端查表 → 打所有权校验（§四 越权）；网关统一鉴权 → 打路径归一化差异与白名单（§六）；前端路由 → **直接调 API**（大概率裸奔）。

## 二、Cookie / Session

### 【判定】
| 观察 | 结论 |
|---|---|
| `Set-Cookie: JSESSIONID=xxx; Path=/; HttpOnly` | 规范部署 |
| 缺 `HttpOnly` | XSS 可直接偷会话（XSS 危害升级证据） |
| 缺 `Secure` | HTTP 明文可截获（报告风险项） |
| 缺 `SameSite`（或 `=None` 无 Secure） | CSRF 面开启 |
| 会话 ID 呈规律（自增/时间戳/base64 解出结构） | **可预测会话**=会话劫持面（高危） |
| 登录后会话 ID 不变 | **会话固定**（Session Fixation） |
| 退出后旧 cookie 仍可用 | 服务端未失效（退出仅前端清 cookie） |

### 【测试】最小验证
```
1. 会话固定：登录前记 cookie → 用同一 cookie 完成登录 → 检查是否换新（不换=成立）
2. 退出失效：退出后重放旧 cookie（一发即停）
3. 并发/过期：多设备登录后互踢策略（业务逻辑，记录进报告）
4. 可预测性：注册两个小号，对比两次会话 ID 的差值/结构（不外推他人 ID——外推=越权尝试，需授权范围内）
```

## 三、JWT（现代架构第一大坑，判定价值最高）

### 【判定】
```
eyJ 开头 + 两个点分三段 = JWT
解 header（base64url 解码，无需密钥）：
  {"alg":"HS256","typ":"JWT"}            → 对称密钥（弱密钥面）
  {"alg":"RS256"}                        → 非对称（混淆面）
  {"kid":"..."}                          → key id（注入面：路径遍历/SQL/命令）
  {"jku":"..."} / {"x5u":"..."}          → 远程密钥获取（SSRF/密钥替换面）
  {"alg":"none"}                         → 无签名（历史配置错误，仍偶见）
解 payload：看字段——sub/uid（身份来源）、exp/iat/nbf（时效）、role/admin（权限声明）、
           iss/aud（签发与受众，缺失=跨系统 token 复用面）
```
**画像三问**：身份字段来自 token 还是服务端会话？权限字段（role）是否被后端信任？token 存哪（localStorage = XSS 可直接读）？

### 【攻击面与判定探针】（**全部在授权范围内、用自己的小号 token 做**）

| 面 | 探针（最小、无害） | 成立判据 |
|---|---|---|
| **alg=none** | 改 header alg 为 `none`/`None`/`nOnE`，去掉签名段，重放 | 200 且业务正常 |
| **HS256 弱密钥** | 本地 jwt_tool/hashcat 跑公开词表（**离线操作，零请求**） | 离线验签成功=可任意伪造 |
| **RS256→HS256 混淆** | 用服务端公钥（`/jwks.json` 或证书，公开可取）当 HMAC 密钥重签 | 200=服务端把公钥当共享密钥用了 |
| **kid 注入** | kid 改成 `../../dev/null`（空密钥）/ `/dev/null` / 路径遍历到已知内容文件 / 含引号看 SQL 报错 | 签名校验被绕过 or 报错泄露 |
| **jku/x5u 远程密钥** | 指向你自己的 HTTPS（提供你的 jwks），重签 | 服务端来取=成立（**同时是 SSRF 证据**） |
| **权限字段信任** | 把自己 token 的 `role:user`→`role:admin`，用弱密钥重签或直接改（若无签名校验） | 越权成立 |
| **iss/aud 缺失** | A 系统的 token 打 B 系统接口 | 跨系统复用成立 |
| **过期不校验** | 把 exp 改成过去（用旧 token 重放） | 仍 200 = 时效未校验 |

> **红线执行版**：所有 JWT 测试用**你自己注册的小号 token**。伪造他人 token/接管他人会话不做了才叫证明——「能用弱密钥离线验签成功」+「能改自己 role 且被接受」两个证据已经构成完整高危报告，不需要真的登录别人。

### 【绕过】JWT 相关防御的常见形态
- 白名单 alg：只允许 RS256 → 混淆攻击失效，转 kid/jku 面
- 签名校验但**不校验 claims**：`sub` 可改（签名覆盖不到的字段？不存在——但常见错误是「校验签名后仍用请求参数里的 userId」= 双源不一致，**这是最高频的真实缺陷**：token 有效但业务用 body 里的 id）
- 前端解析：前端用 JWT 判权限渲染菜单，后端不校验 → 改 token 直接调 API（回到 §一 画像第④问）

### 【学习】
- 工具：`jwt_tool`（本地，功能全）· jwt.io（**别贴真实 token**，用自造的）
- 环境：PortSwigger Academy JWT 全 lab（该主题的最佳教材，lab 优先，答案册纪律）
- 智库：`JWT` · `alg none` · `kid` · `jku` · `HS256 RS256 confusion`（owasp-cheatsheets 里有官方 JWT 篇，反读法见 dojo 02_心智模型/06）
- 验收：能默写上表 8 个面+探针；能解释 RS→HS 混淆的数学原理（一句话版：服务端用同一密钥参数既做 RSA 验签又做 HMAC 校验，攻击者用公开 RSA 公钥当 HMAC 密钥即可伪造）

## 四、越权（水平/垂直）——你的出单主力，判定优先

### 【判定】身份与资源的绑定关系在哪校验
```
观察请求：身份来自 ① Cookie/JWT（不可控） ② body/query 里的 userId（可控！） ③ 路径里的 id
资源标识：自增 id / UUID / 复合 key（userId+resourceId）
判定结论：
  身份可控（②） → 垂直越权几乎必然（改 userId=admin 或换角色参数）
  身份不可控但资源是自增 id → 水平越权高发（IDOR）
  资源是 UUID → 遍历不可行，转「泄漏 ID 的旁路」（列表/搜索/导出/分享链接/前端 JS）
  复合 key → 只校验前缀不校验归属是常见缺陷
```

### 【测试】标准双账号法（**唯一正确的测法**）
```
准备：同一系统两个自有小号 A、B（各建一条可识别的测试数据，如备注写 CANARY_A）
水平：用 A 的凭证请求 B 的资源 id → 看到 CANARY_B = 成立
垂直：用普通号请求管理员专属接口的路径（从管理员页面抓包得到，或从 JS/接口字典推）
异步：B 发起导出任务 → A 用自己的凭证取 B 的 taskId → 拿到 B 的导出文件 = 成立（高频漏点）
批量：单条校验了，批量接口（ids=[1,2,3]）没校验 = 常见
间接：A 能否让 B 触发（分享链接/邀请/评论渲染）= 存储型越权面
```
> 智库仅 36 篇越权、HowToHunt 在你的 vendor_src 里——**这一节 + HowToHunt + 你的双账号实践，就是你的越权主力弹药**。

### 【绕过】越权修复后的残留面（复测与二次发现）
- 修了 GET 没修 POST（同功能多端点）
- 修了单条没修批量/导出
- 加了前端校验（改 JS 或直连 API 即失效）
- 加了网关鉴权但内部端口/管理端口仍可直连（边界③④）
- 用「历史接口版本」（`/api/v1/` 修了，`/api/v2/` 或 `/api/` 老的还在）

## 五、OAuth2 / OIDC（第三方登录，逻辑洞密度最高）

### 【判定】看 URL 参数即可识别
```
/authorize?response_type=code&client_id=X&redirect_uri=Y&scope=Z&state=S
   → 授权码模式（最常见）
/authorize?response_type=token...  → 隐式模式（token 直接在 URL fragment，风险高）
/.well-known/openid-configuration  → OIDC 发现文档（白送全部端点与能力清单）
```

### 【攻击面表】

| 面 | 判定探针 | 危害 |
|---|---|---|
| **redirect_uri 校验松** | 试 `redirect_uri=https://target.com.evil.net`（后缀）· `https://evil.net/target.com`（前缀）· `...?next=evil` · 路径遍历 `/../` · 只改大小写/编码 | token/code 外泄 → 账号接管 |
| **开放重定向 + OAuth** | 目标自有 `?url=` 重定向洞作为 redirect_uri | 绕过白名单的经典组合链（07_SRC/03 §3） |
| **state 缺失** | 授权请求无 state 参数 | **CSRF 绑定攻击**（把攻击者账号绑到受害者，或反向） |
| **code 重放/无限期** | 同一 code 用两次 | 令牌窃取后可用 |
| **scope 提权** | 手改 scope=admin/openid+profile | 拿到超额权限 |
| **client_secret 泄露** | 前端 JS/移动端里含 secret（本应只在服务端） | 可冒充客户端 |
| **token 泄漏渠道** | Referer 头（页面含外链）/ 浏览器历史 / 日志 | 报告风险项 |
| **PKCE 缺失**（公共客户端） | 移动端/SPA 无 code_verifier | code 拦截即可换 token |

### 【学习】PortSwigger OAuth lab 全通；`/.well-known/openid-configuration` 养成条件反射（见到第三方登录先发它）；智库 `OAuth` · `redirect_uri`（api-security-checklist 32 篇里有 OAuth 专项）。

## 六、SSO / CAS / SAML（企业级单点）

| 协议 | 判定 | 高频面 |
|---|---|---|
| **CAS** | `/cas/login?service=`、ticket 参数（ST/PGT/TGT） | `service` 参数白名单松（同 OAuth redirect_uri）；ticket 可重放；登出不彻底（单点登出未同步=会话残留） |
| **SAML** | XML 断言、`SAMLResponse` base64 参数、IdP metadata XML | **签名绕过/XML 签名包装（XSW）**——SAML 的经典深坑；断言重放；`InResponseTo` 缺失；评论注入绕过签名（XML comment 攻击面） |
| **OIDC** | 见 §五 | 同 OAuth + `id_token` 校验缺失（不验签直接信 payload） |
| 自研 SSO | 常见于国产 OA/统一认证平台 | 票据格式可预测（时间戳+MD5）、票据校验接口未授权、跨子系统信任传递断裂 |

> SAML 的 XSW 属于深水区（需要 XML 签名机制理解），学习路径：先在本地用 Keycloak 起一个 IdP 环境，读它的断言，再学 XSW 的各变体（grimoire `SAML` + 智库外补充）。**判定层面你只需要：见到 SAMLResponse → 解 base64 → 看 Signature 是否覆盖整个 Assertion → 不覆盖或可移动 = 有面。**

## 七、密码策略与找回流程（低技术高产出）

| 面 | 判定探针（全部无害、低频） | 说明 |
|---|---|---|
| 用户枚举 | 存在/不存在用户名的响应文案、状态码、**时延**差异（各一发对比） | 枚举面本身就是低危报告项，更是后续攻击的前置 |
| 找回密码 token 弱 | 重置链接的 token 结构（时间戳？自增？MD5(邮箱)？）；**用自己的邮箱**测 | 可预测=任意用户密码重置（严重高危） |
| 验证码面 | 回显（响应里带 code）/ 可复用 / 可删除 / 不过期 / 与账号不绑定（换手机号仍通过） | 07_SRC/03 §4 五连测 |
| 密码策略 | 注册时试 `123456`（**一次**）；改密时试旧密码作新密码 | 策略缺失=报告项（不爆破） |
| 改密不失效会话 | 改密码后旧会话是否仍有效 | 账号盗用后无法踢出=真实危害 |
| 越权改密 | 改密请求里的 userId 可控？（双账号法） | 高危，直接接管 |

## 八、MFA / 二次验证

| 面 | 判定 | 危害 |
|---|---|---|
| 可跳过 | 拿到 OTP 步骤后**直接请求后续接口**（不发 OTP） | MFA 形同虚设 |
| 响应里带结果 | OTP 校验接口的响应体/JSON 里含 `success:true` 或验证码本身 | 前端判定 |
| 无频率限制 | OTP 输错 3 次（**不超过 5 次，且用自有账号**）观察是否锁定 | 可暴力（但你不暴力——只报告缺陷） |
| 绑定不严 | A 账号的 OTP 用于 B 账号流程 | 逻辑缺陷 |
| 备份码/恢复码 | 是否可预测、是否用后失效 | 常见漏点 |
| TOTP 密钥泄露 | 注册 MFA 时 `otpauth://` URI 或 secret 是否出现在响应/日志 | 泄露=可离线生成码 |

> **频率类测试的合规线**：证明「无限制」只需 3-5 次尝试 + 观察无锁定，**不要跑到 100 次**（那变成暴力攻击，触红线且可能触发对方告警）。报告写「未见频率限制，理论上可暴力枚举 6 位码」——推论性描述足够，无需实测。

## 【本篇学习建议】

1. **这一册是你 ROI 最高的学习投资**：无需 payload、无需绕 WAF、单请求即可验证、评级通常高（越权/账号接管普遍高危）、且是你智库最薄的一册。学习顺序：§四 越权（今天）→ §三 JWT（本周）→ §五 OAuth（下周）→ §七 找回流程 → §六 SSO/SAML（深水区，最后）。
2. **双账号法固化为肌肉记忆**：每个新目标注册两个小号是开工第一步（不是可选步骤）。你的越权命中率会因此翻倍——多数人只有单账号，压根测不出水平越权。
3. 建 vault `MOC-认证与会话`（你目前没有这个 MOC，而它是 SRC 出单主力），把本篇八节各建一张卡，每卡记录「我在哪个目标上实测过+结果」。
4. 与 cnvd-lab 的接口：`P03_认证与会话机制全谱` 是它的正课教材（原理层），本篇是**判定与测试层**——两篇对读，P03 讲机制，本篇讲怎么打。
