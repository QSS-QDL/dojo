# 01 · 数据流世界观：所有漏洞都是同一条河

> 心智模型 1/6 ｜ 这是整个 02 目录的地基。后面五篇都挂在这条河上。
> 建议最先读，读两遍。

---

## 一、一句话内核

**所有漏洞，都是「不可信数据」流进了「把它当可信对待的位置」。**

不是「漏洞有一百种」，是**一条河的下游有一百个不该被污染的出水口**。SQL 注入、命令执行、XSS、SSRF、反序列化、路径穿越、SSTI、XXE、越权、提示注入——**全是同一件事的不同出水口**。

一旦你装上这个模型，你不再需要「记住」漏洞类型。你需要的是：**看清这条河，然后挨个检查出水口。**

---

## 二、河的三个部件

```
   [源头 Source]  ──流动──►  [汇点 Sink]
              ▲
              └── [净化 Sanitizer]（可能没有，可能有但能被绕过）
```

### 源头（Source）：不可信数据从哪来

新手以为源头只有「GET/POST 参数」。**真实源头清单**（按被忽略频率排序）：

| 源头 | 常被忽略 | 例子 |
|---|---|---|
| URL 参数 / body | ❌ 都会看 | `?id=1` |
| **HTTP 头** | ⚠️ 经常忘 | `User-Agent`（日志注入/log4shell）、`Referer`、`X-Forwarded-For`（IP 伪造绕白名单）、`Accept-Language`、**`Cookie` 的每个字段** |
| **文件名** | ⚠️ 经常忘 | 上传的 `../../x.jsp`、压缩包里的 **Zip Slip** 条目名、`Content-Disposition` 的 filename |
| **数据库里存的旧数据** | 🔴 **最常忘** | **二次注入**：用户先把 payload 存进 profile，另一个功能把它拼进 SQL/命令 |
| 第三方返回 | 🔴 最常忘 | OAuth 回传的用户名、Webhook、RSS/爬虫抓的外部页面、支付回调 |
| **JSON 的结构本身** | 🔴 最常忘 | 不只是值——**键名**也可能进 SQL（动态排序字段 `orderBy`、动态查询构造器） |
| 环境变量/配置 | ⚠️ | 容器 env、`.env`、云 metadata |
| 时间/顺序 | 🔴 | 竞态条件：源头是「两个请求的相对时序」 |

### 汇点（Sink）：数据在哪被当成指令/特权执行

**汇点是「解释器」**。判断汇点的唯一问题：**这段数据接下来会被谁「解析」？**

| 汇点类型 | 解释器 | 后果 |
|---|---|---|
| SQL 字符串拼接 | 数据库 | SQLi |
| `Runtime.exec` / `system` / `popen` | 操作系统 shell | RCE |
| 反序列化（`readObject` / `unserialize` / `pickle`） | **对象构造器** | RCE（链） |
| 模板渲染（Freemarker/Thymeleaf/Jinja） | 模板引擎 | SSTI |
| HTML 输出 | **浏览器** | XSS |
| `URL` 请求发起（`RestTemplate`/`curl`） | 网络栈 | SSRF |
| 文件路径拼接 | 文件系统 | 穿越/上传 |
| XML 解析器 | XML 引擎 | XXE |
| `include`/`require`/动态类加载 | 语言运行时 | LFI/RCE |
| **LLM 的 prompt** | **模型** | 提示注入（2026 年最大的新汇点） |
| **权限判定表达式** | 鉴权层 | 越权（见下） |

> **关键洞察：越权也是数据流问题。** 「谁能访问这个对象」的判定，如果判定依据（`userId`、`orderId`）来自**请求本身**而不是**会话**，那么源头污染的就是「权限解释器」。这就是为什么 IDOR 的修复不是过滤字符，而是**换源头**（从会话取身份，不信任请求里的身份）。

### 净化（Sanitizer）：以及为什么它总是失败

净化的四种形态，失败率递增：

1. **参数化/预编译**（结构上分离数据与指令）→ 几乎不失败。**唯一真正的解法。**
2. **白名单校验**（枚举允许值）→ 少失败，但常被写成「前缀匹配」「包含匹配」而漏
3. **转义/编码**（按上下文改写危险字符）→ **最常失败**，因为**转义是上下文相关的**：HTML body 的转义 ≠ HTML 属性里的转义 ≠ JS 字符串里的转义 ≠ URL 里的转义。**同一个值输出到三个位置需要三种转义。**
4. **黑名单过滤**（拦已知坏字符）→ **必然失败**。绕过史就是一部黑名单羞辱史。

**审计时你要问的三个问题**（顺序不能变）：

```
① 这条流的源头在哪？（穷举，别只看参数）
② 汇点是什么解释器？（决定需要什么转义/校验）
③ 中间的净化是哪一级？如果是 3 或 4，它假设的上下文和实际汇点上下文一致吗？
```

**第 ③ 问的「上下文不一致」就是绝大多数真实漏洞的根因。** 记住这句话，它值一整个职业生涯。

## 三、怎么在真实代码里追这条河

### 3.1 反向追踪（审计主用法，比正向快 10 倍）

**不要从入口往下读**（分支太多，读不完）。**从汇点往上追**：

```
步骤 1: 列出汇点函数名 → grep 出所有调用点
步骤 2: 对每个调用点，看参数是不是变量
步骤 3: 变量往上追，直到追到「Controller 方法签名 / req.getParameter / @RequestBody」
        → 追到了 = 有洞；追到常量/配置 = 放过
步骤 4: 中途遇到的每个「过滤/校验」函数，进去读一遍，判断是白名单还是黑名单
```

这就是 `cnvd-lab/tools/mybatis_dollar_scan.sh` 和 `audit_grep.sh` 在做的事。**你现在知道它们为什么长这样了**——它们是「步骤 1」的自动化。

> **学习建议**：不要满足于跑脚本。手动做 5 次完整的四步追踪（用 `cnvd-lab` 雷达表里已部署的系统），你才能建立「看到 grep 结果就知道该往上追什么」的直觉。脚本给候选，判断给结论。

### 3.2 正向追踪（黑盒主用法）

黑盒看不到代码，但**数据流依然可观测**。方法：**注入一个可追踪的标记值**（canary），看它出现在哪：

| 你在 `?q=CANARY123` 送进去 | 你观察到 | 说明流到了 |
|---|---|---|
| 页面 HTML 里出现 CANARY123 | 反射输出 | HTML 汇点（XSS 面） |
| 出现在 `<script>var x="CANARY123"</script>` | 进了 JS 上下文 | **需要 JS 转义，HTML 转义无效** |
| 出现在 `Location: /search?q=CANARY123` | 进了响应头 | CRLF 面 |
| 报错信息里出现 `... near 'CANARY123'` | 进了 SQL 语句 | **SQL 汇点已确认** |
| 出现在另一个页面/邮件/日志/导出文件 | 被存储了 | **二次注入面 + 存储 XSS** |
| 出现在别的用户看到的页面 | 跨用户传播 | 存储 XSS 打管理员（最有价值的发现） |
| 完全消失 | 被丢弃或过滤 | 查过滤点，或换源头（改 Cookie/Referer 再试） |

> **canary 是黑盒数据流分析的全部秘密。** 一次请求送 5 个不同 canary 到 5 个不同源头（参数/Cookie/UA/Referer/文件名），比送 100 个 payload 到 1 个源头信息量大得多。

### 3.3 断点定位：过滤发生在哪一层

payload 被拦了，**先别急着找绕过，先定位是谁拦的**。三层各有特征：

| 拦截者 | 特征 | 应对方向 |
|---|---|---|
| CDN/WAF（网络层） | 拦截页有明显厂商标识、返回码常是 403/405、**后端日志无记录** | 换编码/换协议版本/换参数位置（见 05 篇） |
| 框架/中间件 | 报错带框架名、400 且 body 是框架默认页 | 找框架解析器的边界 |
| 应用代码 | 业务文案「非法字符」「参数错误」、**200 但业务码非 0** | 看它过滤了什么字符，白名单还是黑名单 |

**定位方法**：送一个绝对无害但会反射的 canary → 再送 canary+单个特殊字符（`'`、`<`、`"`、`../`）→ 观察哪个字符触发了拦截、返回码/文案怎么变。**三个请求就能画出这层的过滤轮廓。**

## 四、这个模型怎么帮你「从一个洞推出一类洞」

因为**所有洞都是同一条河**，所以：

- 你在 A 系统找到 `orderBy` 参数的 SQL 注入 → **不是「A 系统的 orderBy 有洞」**，而是「**动态排序字段这个模式**有洞」。
- 于是你去找：**哪些系统用了同一个框架/同一个代码基**？（若依生态、JeecgBoot 生态、同一套 CMS 的衍生站）→ 这就是 `cnvd-lab/docs/01` 说的「杠杆 A」，也是 CNVD 通用型的来源。
- 于是你去找：**同一系统里还有哪些「结构被数据影响」的点**？动态排序、动态表名、动态列名、动态 `IN(...)`、MyBatis `${}` vs `#{}`。
- 于是你去查：**这个模式的官方修复建议是什么**，然后看哪些系统「按老写法写」→ 批量候选。

**一次发现 → 一个模式 → 一批目标 → 一个通用漏洞。** 这条链是你 D25 交 CNVD 的思维骨架。

## 五、练习（30 分钟，今天就能做）

选一个你雷达表里已部署的系统（本地 Docker，符合你的红线）：

1. 用 canary 法测 5 个源头（参数/Cookie/UA/Referer/上传文件名），记录每个 canary 出现在哪（15 分钟）
2. 挑出现最多的那个汇点，手动做反向追踪：grep 汇点函数 → 追到入口（10 分钟）
3. 写一条 vault 笔记，标题格式：`数据流-<系统名>-<源头>到<汇点>.md`，正文四段：**源头 / 流动路径 / 汇点 / 净化在哪一级**（5 分钟）

> **验收标准（可核对）**：
> - [ ] 能背出「三个问题」的顺序和内容
> - [ ] 能说出至少 4 个「常被忽略的源头」
> - [ ] 完成了上面 30 分钟练习，vault 里出现那条笔记
> - [ ] 给你一个新漏洞类型（比如「CSV 注入」），你能在 30 秒内说出它的源头/汇点/净化失败原因

> **智库检索词**（带着模型去查，别漫游）：
> `二次注入` · `MyBatis ${}` · `Zip Slip` · `orderBy injection` · `log4shell header` · `SSRF 内网` · `XSS 上下文`
> 每查一个，只回答一件事：**它的源头是什么、汇点是什么、净化为什么失效？** 三句话记进 vault，不要复制正文。
