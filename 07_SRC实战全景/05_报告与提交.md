# 05 · 报告与提交（16 情境）

> 报告是 SRC 的**产品**，漏洞只是原料。同样的洞，报告质量决定评级、审核速度和你的信用画像。
> 通用模板与 CNVD 细则在 cnvd-lab `docs/05`，本篇只管「出了状况怎么办」。

---

**§1 报告被驳回「非漏洞」**
- 症状：你认为是洞，平台判「不构成漏洞」。
- 处置：三步走——①**读驳回理由原文**，对照平台漏洞收洞细则（多数驳回是「不在收洞范围」而非「你错了」：如纯 self-XSS、无法证明影响的逻辑问题、目标自有资产的正常功能）；②自查证据链（04 篇 §16 五件套）：是不是「影响没讲到」而不是「洞不存在」→ 补影响链叙事后申诉一次；③确属平台不收的洞型 → 记入你的「平台口味表」（01 篇 §4），此类洞转投 CNVD 或换平台。
- 止损线：申诉一次为限。反复缠申诉会被标记为「难缠提交者」，影响你所有后续报告的审核体验。

**§2 被判重复**
- 处置：04 篇 §19 的技术侧自查之外，申诉的**证据形态**：并排对比表（你的接口/参数/触发路径 vs 首个提交的公开信息），主张「不同实现点=不同漏洞」时附各自独立的复现请求。若平台判重规则写明「同一影响面即重复」→ 不申诉，接受。
- 学习建议：被判重不是坏事，是免费的「热门度情报」——该目标该洞型已被覆盖，写进雷达表备注。

**§3 被降级（高危判中危/中危判低危）**
- 症状：洞收了，评级比预期低。
- 处置：申诉的弹药只有三种，按优先级——①**引用平台自己的评级细则原文**（「贵平台细则 X 条：可获取用户敏感信息的越权应评为高危」——引用原文的申诉成功率远高于讲道理）；②**补充影响链证据**（04 篇 §10：降级多因影响没讲透，补一个「影响升级证据」再申诉）；③**CVSS 向量作辅助**（给出向量串和各分项理由——注意：国内平台多以自有细则为准，CVSS 只作说理工具不作裁决依据）。
- 止损线：一轮申诉维持原判 → 接受。评级差额的期望值 < 你时间投入的下一单期望值。

**§4 被标「已知问题/不予修复」**
- 症状：平台回复「厂商已知悉」。
- 处置：①要求书面确认「已知悉的时间点」——如果你提交在前，多数平台规则仍计你的分/赏（提交时间戳是你的，git 一样不可篡改）；②「不予修复」的商业决策类（风险接受）→ 换角度重新定性：同一缺陷换个影响叙事（如「测试环境弱口令」被接受风险 → 强调其可达生产网段）再提一次**是骚扰，不做**；正确动作是记录+泛化到同家族其他厂商；③CNVD 侧「已知问题」不影响你投通用型（对象不同：厂商已知 ≠ CNVD 已收录）。

**§5 审核要更多信息**
- 症状：审核评论「请补充 XX」。
- 处置：24 小时内响应（响应速度影响审核员对你的印象分）；补充材料按「他问什么给什么+一点点点前瞻性」（问复现步骤给黄金标准版；问影响给影响链叙事）。**不要**借补充之机扩大验证深度去「演示更严重的危害」——补充证据用已有材料重组，需要新动作的（如再取一条数据）先想红线（04 篇 §15 单条即停仍适用）。

**§6 厂商不响应**
- 症状：提交后超期无审核/无修复确认。
- 处置：①查平台超期规则（多数平台有「N 天未处理自动流转/仲裁」条款，引用它）；②平台客服工单催办（书面、一次、礼貌）；③仍无果 → 记录该平台/厂商的响应画像进你的平台口味表（响应慢的厂商=你的现金流黑洞，未来选题降权）。**不要**自行公开披露催办（见 §16）。

**§7 平台与厂商互相踢皮球**
- 症状：平台说等厂商确认，厂商说找平台。
- 处置：所有沟通集中在**平台工单**里（单一事实源，别在微信/QQ 上分散沟通——书面且可仲裁）；工单里把时间线列成表（X 日提交/X 日厂商查看/X 日超期），要求平台按规则裁决。皮球局 90% 靠「引用规则+时间线表格」解决，10% 靠升级客服。

**§8 修复复测被拒/修复争议**
- 症状：厂商说修了，你复测发现还能打（或厂商说你复测方式不对）。
- 处置：①复测用**与原报告完全相同的请求**（同账号同路径），差异结果并排贴出（原始 payload 成功截图+时间戳）；②厂商加了 WAF 规则挡你的 payload → 主张「外挂防护≠代码修复」，附「绕过该规则的等价 payload 仍生效」证据（**等价验证一个即停**，不是秀绕过大赛）；③平台仲裁时你的立场：修复标准=「缺陷根因消除」，不是「我的特定 payload 失效」。

**§9 报告泄露风险**
- 症状：担心报告内容外流（厂商拿你的报告去修洞不给钱/内容被转卖）。
- 处置：①平台内提交的报告有平台记录，时间戳即你的权属证据（这也是「必须走平台」的原因之一，01 篇 §17）；②给厂商的补充材料**不含可武器化的完整链**（复现步骤够证明即可，不给「顺便帮你们把其他洞也测了」的加料）；③高价值通用型走 CNVD（有证书+编号制度，权属最硬）；④公开输出（dojo 06_成长系统/02）永远等修复+披露期之后。

**§10 CNVD 通用型 vs 网站洞怎么选**
- 症状：一个洞两边都能投？
- 处置：判定看**对象**——漏洞在「产品/组件本身」（任何部署实例都有）→ CNVD 通用型（证书+编号，长期资产）；漏洞在「该网站的实现/配置」（换个部署就没有）→ SRC 平台（赏金）。两者冲突时（同洞可归两类）：**先 CNVD 后 SRC 会卡**（CNVD 收录后部分平台判「已公开」降收），**先 SRC 后 CNVD 通常可行**（网站洞修复不阻碍通用型论证，但要在 CNVD 报告里用你自己的部署环境证明通用性，不依赖 SRC 目标）。拿不准 → 用本地部署的同款产品重新验证一遍通用性，两边证据各自独立成立，两不耽误。

**§11 CNVD 编号被驳回**
- 症状：通用型提交被驳回。
- 处置：对照 CNVD 门槛（cnvd-lab `docs/00` 有规则细则）自查三大常见死因——①**通用性证明不足**：只给了一个在线目标的证据 → 用「产品官方发布包/版本号+本地部署复现」重做证据（通用型的证据主体是产品不是网站）；②**版本区间不清**：「某产品有洞」→ 必须精确到「V x.y ~ V x.z 受影响，V w 已修复」（补丁 diff 流水线就是为这个服务的，dojo 04 篇）；③**已收录重复**：先搜 CNVD 库（编号/产品名），撞了就换成员或换洞。驳回可补充材料重提，**别换壳重复提交同一问题**（记录在案，影响后续）。

**§12 证书申请卡住**
- 处置：CNVD 证书有申请窗口和流程周期（颁发慢是常态）；卡住超过公示周期 → 官方渠道书面查询进度（工单/邮件，附提交编号）。证书是年度审核/求职材料的硬通货，建立「提交→收录→证书」跟踪表（cnvd-lab `data/提交台账.csv` 加两列状态），每季度核一次账。

**§13 多个平台能否重复提交**
- 处置：**同一漏洞同一目标：不能**（各平台规则均视为重复提交/一洞多投，发现即封号级处罚）。**同一漏洞不同目标实例**（家族泛化的产物）：可以，各投各的（每个实例是独立漏洞）。**网站洞与 CNVD 通用型**：见 §10 的时序策略。底线原则：任何「一洞多吃」的想法都先过一遍平台规则原文——封号损失的是你全部存量信用。

**§14 报告里能不能放 payload**
- 处置：放**复现所需的最小 payload**（证明缺陷存在的那一个），不放「武器化增强版」（批量利用脚本/免杀变体/完整 exploit 链）。报告的目标是「审核员能复现+厂商能修复」，超出这个范围的攻击性内容：①增加你的法律暴露面；②让厂商把你当威胁而不是帮手；③部分平台明令禁止。修复建议段反而要**加料**（代码级修法，这是你的专业名片，06_成长系统/02 §级2）。

**§15 截图打码标准**
- 处置：固定标准（做成截图工具的动作习惯）——**打码**：真实用户姓名/手机号/证件号/订单金额明细/凭据密钥/token；**保留**：URL 栏、系统时间、证明漏洞的关键字段名和结构（值可打码，**字段名和条数留着**——「可见 47 条记录，内容已打码」比全糊的图证明力强）；**加分项**：截图里带上你的测试账号标识（证明用的是自有小号）。一句话：打码打到「厂商能确认问题、外人拿不到数据」的平衡点。

**§16 提交后厂商迟迟不修，要不要披露**
- 处置：默认**不披露**。披露的合法路径只有三条：①平台规则允许的披露条款（部分平台有「超期 N 天可申请公开」流程——走流程，不自行公开）；②厂商书面同意；③CNVD 等官方渠道的公开（由官方执行，不是你）。自行披露未修复漏洞=把厂商推到对立面+可能触犯法律（提供侵入程序工具/帮助罪的边缘），且行业名声一次清零。「用披露施压催修」这个念头出现时，改用工单催办（§6）。

## 【本篇学习建议】
1. 本篇 16 卡有 9 卡是「争议处理」——争议的共同心法：**书面、引规则、给时间线、一轮为限**。把这 12 个字贴在报告目录旁边。
2. §10 的 CNVD/SRC 分流判定和 §15 打码标准，合并进你的报告模板（cnvd-lab docs/05）做成提交前自查表，一次模板升级终身受益。
3. 每次驳回/降级/判重都记一行进「平台口味表」——半年后这张表就是你比新入场者多出来的全部信息优势。
